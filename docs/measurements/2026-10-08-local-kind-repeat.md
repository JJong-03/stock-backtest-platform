처리량 중간값은 **약 57% 증가**했다: `(56.85 / 36.29 - 1) × 100`.
분당 처리량은 `성공 건수 / 20건 전체 완료 시간 × 60`이며, 위 중간값은 회차 5개의 처리량 중간값이다.
p95는 구성별 성공 요청 100건의 클라이언트 완료 시간을 정렬한 95번째 값이다.
완료 시간은 요청 제출부터 클라이언트가 성공을 확인할 때까지로, 2초 폴링과 결과 차트 생성 시간을 포함한다.
웹 컨테이너 최대 메모리는 회차별 `memory.peak` 중 최댓값이며 워밍업도 포함한다.

## 해석과 한계

- 이번 반복에서도 C 설정의 처리량이 높았다. 워커 수와 CPU/메모리 한도를 함께 바꾼 설정 비교이며, 알고리즘 개선이나 동일 자원 대비 효율 개선을 측정한 것이 아니다.
- 9월의 +58%는 당시 각 구성 1회의 결과다. 이번 실험은 워밍업, 웹 Pod와 DB 초기화, 반복 순서가 명시된 별도 실험이므로 당시 절대값을 대체하거나 합쳐 평균 내지 않는다.
- 로컬 단일 노드와 같은 입력 요청만 검증했다. 실제 클라우드, 여러 사용자/전략의 혼합 부하, 장시간 안정성, 장애 주입은 검증하지 않았다.
- Worker 시작/완료 시각은 DB에서 초 단위이므로 계산 자체의 시간을 정밀하게 비교할 수 없다.
- 차트를 조회 때마다 다시 만드는 동작은 그대로다. 이 결과는 해당 동작 아래에서 자원/워커 구성을 비교한 값이다.
- 5회 반복의 중간값과 범위를 제시했으며, 통계적 유의성이나 운영 SLA를 주장하지 않는다.

## 재현 순서

1. [기존 측정의 환경 구성 절차](2026-09-25-local-kind-load.md#다시-재는-방법)로 별도 kind 클러스터를 만든다. 전용 kubeconfig를 지정하고 위 이미지와 MySQL 8.0.36을 사용한다.
2. 별도 클라이언트 Pod에 현재 `measure_local_load.py`를 ConfigMap으로 마운트한다.
3. 표의 순서대로 Deployment의 웹 워커/CPU/메모리 설정을 적용하고, 매번 Pod를 교체해 Ready를 기다린다.
4. **측정 전용 DB에서만** `TRUNCATE TABLE backtest_results`를 실행하고 아래 명령을 클라이언트 Pod에서 수행한다.
5. 각 회차 JSON과 측정 전후 웹 Pod의 restartCount, memory.peak를 보관한다. 완료 후 측정 클러스터를 삭제한다.

```bash
python /measure/measure_local_load.py --base-url http://web \
  --sequential 2 --concurrent 20 --out /tmp/round-01.json
```
